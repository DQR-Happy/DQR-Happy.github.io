Measurement

Define the endpoint before comparing performance

Kernel time, generation time, and complete collection time answer different questions.

Qirui Deng / 邓骐睿2026-11-154 min read
On this page
  1. Time the work your claim is about
  2. Use phases to explain the total
  3. Separate correctness validation from performance measurement
  4. A useful minimum measurement record

Time the work your claim is about

A faster GPU kernel does not necessarily make a request faster. Synchronization, host scheduling, transfers, and file output can change the end-to-end result. If a tracing system is evaluated on delivering a complete trace, its endpoint should include the final output and file close, rather than stopping at the end of generation.

Use phases to explain the total

Prefill / first-token, decode, and trace-drain phases help locate overhead. However, encoding, transfers, and computation can overlap in a pipeline. Their separately measured durations cannot simply be added. Define phase boundaries within the same run and retain the complete-request total as the basis for the claim.

Separate correctness validation from performance measurement

Full-field comparisons, an extra raw-record oracle, and whole-output hashes belong in dedicated correctness runs. Range checks, format checks, and raw fallback required by the algorithm remain part of its timed path. Subtracting a cost measured in a different diagnostic run does not produce a measured performance result.

A useful minimum measurement record

Record hardware and software versions, model and input identities, precision, capture scope, warm-up, the repetition unit, method order, timing boundaries, failed attempts, and output size. Distinguish serial raw from asynchronous raw, and collection from offline analysis. A number becomes comparable only when these boundaries are explicit.
