Inference systems

From an optimization option to execution evidence

Selecting an option does not prove the intended optimization ran.

DQR-Happy2026-11-153 min read
On this page
  1. Distinguish requested, resolved, and effective
  2. Build a traceable comparison
  3. Agreement is not correctness
  4. Keep missing evidence visible

Distinguish requested, resolved, and effective

The requested configuration, the runtime-resolved plan, and the implementation that actually executes can differ. Precision or fusion options may fall back because of shapes, device capabilities, missing artifacts, or version constraints. Before comparing performance, identify the loaded implementation, execution sites, call evidence, and fallback reasons.

Build a traceable comparison

Retain identities for the model, tokenizer, input, artifacts, and source. Fix output budgets and decoding policies, record actual input / output token counts, and associate results with a run ID. Diagnostic runs explain mechanisms; independent performance runs estimate speed; quality runs evaluate numerical and task behavior.

Agreement is not correctness

Matching outputs establish agreement on that task, not correctness. Fixed-answer tasks can be scored separately; open-ended generation needs a task-appropriate evaluation. Producing a low-bit weight artifact likewise does not prove that deployment uses low-bit computation.

Keep missing evidence visible

Unavailable multi-GPU hardware, missing counter permissions, and unimplemented optimizations should have explicit states. Replacing missing metrics with zero or mixing demonstration data into real runs makes later comparisons unreliable. An experiment platform should preserve room for failures, fallback, and incomplete validation alongside improvements.
