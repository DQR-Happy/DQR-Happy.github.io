性能计时：先定义终点，再讨论快慢

Kernel 时间、生成时间与完整采集时间，回答的是三个不同的问题。

比较什么，就把什么计入时间

一个 GPU kernel 更快，不一定意味着一次请求更快。同步、主机调度、内存拷贝和文件输出，都可能改变端到端结果。评价追踪系统时，如果目标是得到可用的完整 trace，计时终点就应包含最后一份数据写出并关闭文件，而不只是模型生成结束。

分阶段解释，总时间下结论

可以将总时间拆成 prefill / 首 token、decode 和 trace drain 等阶段，定位开销落在哪里。但流水线中的编码、拷贝和计算可能重叠，不能把各操作单独测得的耗时简单相加。阶段边界必须在同一次运行中定义清楚，总时间仍是判断完整请求成本的依据。

让正确性验证和性能测量各司其职

完整字段比对、额外的原始记录 oracle 与全量哈希，适合独立的正确性运行。算法实际路径需要的范围检查、格式检查和 raw 回退，则必须保留在性能路径中。不要从另一轮诊断时间里减掉某项开销，拼出一个没有实际测过的结果。

一份最小可用的测量记录

记录硬件与软件版本、模型与输入身份、精度、捕获范围、预热、重复单位、方法顺序、计时起止点、失败尝试和输出体积。区分串行 raw 与异步 raw，也区分采集运行与离线分析运行。同一个数字，只有在这些边界清楚时才有比较意义。
